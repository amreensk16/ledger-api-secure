# Design decisions and trade-offs

## Dual-signing (keyless + static key) instead of a keyless Kyverno attestor

**Decision:** sign every image twice - keylessly (Task 2's requirement) and
with Task 1's existing static key pair (keeps the live admission gate
working) - rather than adding a second, keyless attestor entry to Task 1's
`require-signed-images` ClusterPolicy.

**Why the alternative was rejected, not just avoided:** keyless verification
anchors trust to the signed Rekor entry's `integratedTime`, not wall-clock
time - that's the whole point of the Fulcio+Rekor pairing (a ~10-minute
certificate plus a permanent log entry, so verification stays valid long
after the cert expires). Skipping tlog verification (`ignoreTlog: true`,
the same workaround the static key already uses, for the same
corporate-proxy reason) removes that anchor, so verification falls back to
checking the Fulcio cert's raw `NotBefore/NotAfter` - which is only valid
for about 10 minutes after signing. ArgoCD's reconciliation loop plus pod
scheduling time can plausibly exceed that window on any given sync. A live
admission gate that intermittently and unpredictably rejects legitimate
deploys depending on timing is worse than not having one. Dual-signing
sidesteps the problem entirely and is *more* rigorous where it counts: the
keyless signature is verified fully tlog-backed, immediately, on GitHub's
unconstrained network, inside the same CI job - stronger evidence than a
degraded no-tlog admission check would have provided anyway.

## Hand-rolled SLSA-style provenance instead of the official `slsa-github-generator`

**Decision:** build a predicate JSON manually and attach it with
`cosign attest --type slsaprovenance`, rather than use
`slsa-framework/slsa-github-generator`'s container builder reusable
workflow.

**Why:** the official generator stores its attestation via the OCI 1.1
Referrers API - the exact registry feature Task 1 already confirmed GHCR
doesn't reliably implement (`MANIFEST_UNKNOWN` on a direct API probe).
Reusing the same cosign v2.4.1 legacy-tag storage path already validated
for the signature keeps the attestation consistently discoverable, for the
same underlying reason.

**Honest trade-off, stated plainly:** this attestation is **self-attested**
- generated by the same job and identity that built the image. The
official generator's entire value proposition is an *isolated* builder
identity that the calling workflow cannot influence, so a compromised build
step can't forge its own clean provenance. This repo's provenance is
"SLSA-inspired," not independent-builder SLSA level 3. Documented here
rather than overclaimed in the README.

## Trivy CVE handling: fix what's fixable, time-box what isn't

Two genuinely fixable HIGH CVEs (`jaraco.context`, `wheel`, vendored inside
`setuptools`) were found in the stock `python:3.11-slim` base image and
fixed by explicitly upgrading `pip`/`setuptools`/`wheel` in the Dockerfile.

Two further findings (`msgpack`, `setuptools` again, under different
versions) are embedded in CPython's own `ensurepip` bundle and pip's
internal vendor directory - static artifacts belonging to the Python
distribution itself, not reachable through this Flask app's runtime
behavior, and not something any `pip install` can upgrade. These are
tracked in `task-2/trivy/.trivyignore` with an `exp:2026-10-30` date and
documented reasoning, rather than silently ignored - the pipeline will
re-block on them once that date passes, forcing a deliberate re-triage
(most likely: check whether a newer `python:3.11-slim` patch release ships
an updated `ensurepip` bundle, or strip `ensurepip`/pip's vendor directory
from the final image as a follow-up hardening step).

## Namespace-scoping Task 1's Kyverno policies to `payments`

**Decision:** `require-non-root-user` and `disallow-latest-tag` were
narrowed from cluster-wide to `namespaces: ["payments"]`, matching how
`require-signed-images` was already scoped.

**Why:** installing ArgoCD's Helm chart failed outright - its own
pre-install Job in the `argocd` namespace was rejected by
`require-non-root-user`, since that policy had no namespace filter and
applied to every Pod cluster-wide, including third-party infrastructure
charts this project doesn't author and can't always control the
`securityContext` of. Scoping to `payments` fixes this and is arguably the
more correct design in the first place: these are ledger-api's own
guardrails, not a cluster-wide platform mandate. Verified this changed
nothing about Task 1's existing rejection demonstrations, since every
insecure-baseline fixture and ad-hoc test pod was already applied into the
`payments` namespace specifically.
